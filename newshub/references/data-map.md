# NewsHub Skill — 数据地图（第三层，按需读）

回答「这条信息有多可信、从哪来、还能从哪里补」之前读这份。具体收录了哪些信源随部署变化，
以 `https://wqu.guru/api/public/sources` 和返回条目的 `source` / `url` 为准；本文只讲**怎么读**。

## 1. 信源形态：从条目的 `url` 判断

| 形态 | `url` 特征 | 典型内容 | 可信度层级 |
|---|---|---|---|
| 官方一手 | 厂商官网博客、`github.com/<org>/<repo>/releases`、官方 changelog、交易所公告页 | 发布、发版、上币下架、规则变更 | **一手**：事实以它为准 |
| 媒体 / Newsletter | 新闻站、`substack.com` 等 | 报道、评论、长文拆解 | **二手**：转述可能有误差 |
| 社群快讯 | `t.me/…`（Telegram 频道） | 速报、行情异动、传闻 | **快讯**：快但未核实，单一来源时要标「待核实」 |
| X 帖子 | `x.com/<handle>/status/…` | 一手人物发言、KOL 观点、合作推文 | 本人账号发言算一手；转述与观点按 KOL 看待 |
| 公众号 | `mp.weixin.qq.com/…` | 中文媒体和自媒体文章 | 按发布方判断，多数是二手 |
| 访谈 / 播客 | `youtube.com/…` | 访谈和演讲（摘要来自转写） | 发言人原话的二手摘要 |

- 聚合源（X List、公众号聚合、Telegram）里的条目，`source` 字段已经**穿透到具体账号或频道的显示名**，
  可以直接用 `items?source=<显示名>` 取这个账号的全部。账号的 handle 不单独返回，但能从 `x.com/<handle>/…` 的 url 读出，`q=<handle>` 也能搜到。
- 多源印证：`/hot` 的 `duplicateCount` 是除代表条目外还有几家**不同信源**报道了同一事件。
  这个数越大，事件越确定；官方一手加多家媒体，比十条快讯更可靠。

## 2. 各数据集的特殊字段与口径

| 数据集 | 特殊之处 |
|---|---|
| `ai` | `mode=all`（含 `q=` 检索）排除 `paper`，要论文必须加 `category=paper`；精选里有论文名额；`tip` 是技巧与观点，多来自个人账号 |
| `invest` | 量最大；交易所公告是上币、下架、维护的一手来源；快讯类信源多，同一事件常有大量重复报道，先看 `/hot` 和 `/events` |
| `ship` | `tags[0]` 是影响性质：`破坏性` > `弃用` > `安全` > `新功能` > `修复`，回答「会不会打断我」；`score` / `selected` 回答「值不值得看」，两者可能背离。按影响性质取条目用 `items?tag=破坏性` |
| `biz` | 方法与拆解为主，内容常青；聚类稀疏，日报常有空版块。适合「怎么做」类问题，不适合「今天发生了什么」 |
| `collab` | 一个 X List 里中文创作者的品牌合作推文。`tags[0]` 是活动品牌；`score` 评的是稿件写法。**只记录、不评判**：不判断是否商业关联或未披露 |

## 3. 每条数据能拿到什么

| 字段 | `/items` | `/hot` | `/events` | `/daily` |
|---|---|---|---|---|
| 原文链接 | `url` | 代表条目的 `url` | 每条报道的 `url` | `sourceUrl` |
| 中文摘要 | `summary` | 无 | `summary` | `summary` |
| 分类 / 分数 / 精选 | 有 | 无 | 有 | 版块即分类 |
| `tags` | 无（但可用 `tag=` 过滤） | 无 | 有 | 有 |
| 多源印证 | 无 | `duplicateCount` + 信源名 | 全部成员报道 | `duplicateCount` |
| 时间范围 | 最近 7 天 | 最近 72 小时 | 不限 | 按 UTC 日，存档可回溯数月 |

条目接口都**没有**：原文全文、播客完整转写、粉丝数、互动量、报价、行情价格。粉丝数和推文互动量只在榜单里有（见下节）。

## 4. 时间口径

- `publishedAt` 是原文发布时间（UTC）。`/items` 按它倒序；`/events` 的 `reports` 按它正序。
- 日报按 **UTC 日历日**切片，不等于「过去 24 小时」。北京时间的「今天上午」可能落在 UTC 的前一天。
- `since` 早于 7 天会被静默 clamp 到 7 天前，所以「过去 30 天」不能靠 `items` 回答，要走日报存档。

## 5. 创作者榜单（`/api/public/rank*`，与条目数据分开）

| 问题 | 怎么读 |
|---|---|
| 覆盖谁 | 第三方公开日榜上出现过的**中文** X 创作者（昵称或简介含汉字）。不是全网排名；英文账号、没上过日榜的人都没有 |
| 涨粉榜口径 | 近 7 天**净增** = 窗口末日粉丝 − 窗口前一天粉丝（取逐日粉丝历史），≥1,000 且粉丝 <100 万才上榜，按净增排。`pct` 只是第二个数字 |
| 分档 | `small` <1 万、`mid` 1–10 万、`large` 10–100 万。「涨得最多」默认指净增；问涨幅时要说明小号的涨幅天然更高 |
| `approx` | 还没拉到逐日历史，数字是日榜加总（日榜每天只列前 500，掉粉的日子不在榜上），**偏高**；引用写「约」 |
| `posts` | 上日榜那几天记录的发帖数之和，缺席的日子不计，只作参考，不要当成发帖总数 |
| 活跃榜口径 | 只看采集器跟踪的创作者近 7 天 ≥20 赞的推文，取互动最高的 5 条（赞 + 2×转发 + 3×引用）之和 ÷ √粉丝；回复不算 |
| 概要 | 每档前 15 名才有 `title` / `summary`，由模型依据本人互动最高的推文写成，只描述内容；其余为空串，不是缺数据 |
| 互动数 | 推文的 `likes` / `retweets` / `replies` / `views` 是**采集那一刻**的读数，之后还会涨；写「截至采集时」 |
| 时间 | 窗口按 UTC 日；`history[].day` 是 UTC 日；推文 `createdAt` 是 unix 毫秒 |

- 榜单只记录、不评判：不设人工黑名单，八卦号、互关号照常列出；色情、博彩、诈骗引流类内容的人不上榜。
  所以「榜上有」不代表推荐，「榜上没有」也不代表什么。
- 头像 `avatar` 是站内路径（拼 base URL）；个人主页 `https://x.com/<username>` 是唯一可以拼的链接。
- 榜单与 collab 是两份数据：collab 记录合作推文（来自一个 X List），榜单记录粉丝变化。同一个人可能两边都有，
  按 handle 对齐；不要从一边推断另一边。
